# Download page routing

Elliott authorized publishing this routing fix on October 31, 2026 after a desktop invitation QR opened the old scan page on his phone.

`/share` now loads the shared device router. iPhone and iPad navigate to the App Store. Android navigates to Google Play. Desktop visitors retain the QR and both explicit store choices. A plain manual store link remains available if a phone browser prevents automatic navigation.

The QR destination is `https://invite.thequestsapp.com/api/download`. This Cloudflare Pages function returns an empty HTTP 302 response directly to the App Store for iPhone/iPad user agents and Google Play for Android user agents. It uses the existing `/api/*` function route. No HTML, CSS, fonts or browser JavaScript are required for the mobile redirect. Destinations are fixed, query parameters are discarded, write methods return 405, and responses are not cached across devices.

Desktop, unknown devices and iPads with a Macintosh desktop user agent go to `https://thequestsapp.com/share?v=3` to bypass cached copies of the older download page. That page retains touch-based iPad detection and both manual store links. Its inline redirect runs in the document head before styles and body content, with no external script, font, animation or stylesheet dependencies. The phone fallback shows only an Opening message and the relevant manual store link on a white background. Desktop visitors see a simple QR and store links. Older QR codes targeting `/share?v=2` continue to work through the existing client-side fallback. The QR asset has a new version query to avoid reuse of the old image. QR generation is self-hosted and includes no phone number or credential.

Elliott reported the earlier QR opened Chrome and then the App Store. The October 31 comparison found that Stompers displays separate App Store and Google Play QR codes, while Whatnot's download link uses AppsFlyer OneLink. An iPhone request to the observed Whatnot link returned an empty 301 response to its App Store listing. Quests now uses a first-party server redirect to preserve one code for both platforms. A phone's camera, default browser and operating system still control the visible handoff; a browser may appear briefly or remain in the background. This change removes the Quests landing-page load from the normal mobile QR route. It does not guarantee a browser-free handoff on every device.
